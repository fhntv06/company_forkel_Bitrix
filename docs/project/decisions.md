# FORKEL — Project Decisions

## 1. Назначение

Документ фиксирует согласованные продуктовые и технические решения, которые должны соблюдаться всеми ролями и сессиями Claude.

Наличие требования в `requirements.md` не означает, что соответствующее техническое решение уже принято.

## 2. Правила принятия решений

1. Не менять существующую архитектуру без обоснованной необходимости.
2. Перед изменением проверять фактическую реализацию и связанные зависимости.
3. Не считать предположение подтверждённым решением.
4. Если решение влияет на архитектуру, безопасность, данные, интеграции или совместимость, сначала описать варианты и последствия.
5. Если решение выходит за рамки назначенной задачи, запросить согласование.
6. Не отменять ранее принятое решение молча: зафиксировать причину и последствия.
7. При противоречиях между документами указать конфликт и запросить уточнение, если он влияет на реализацию.

## 3. Источники истины

При работе использовать следующие источники по назначению:

| Вопрос | Источник |
|---|---|
| Как приложение реализовано сейчас | Исходный код и конфигурация репозитория |
| Как должно работать приложение | `docs/project/requirements.md` и утверждённые уточнения |
| Какие решения согласованы | Этот документ |
| Что уже проверено и выполнено | `docs/workflow/current-state.md` |
| Кто может менять конкретные файлы | `docs/workflow/roles.md` |
| Как должен выглядеть интерфейс | `docs/design/design-system.md` после утверждения |
| Что делать дальше | `docs/workflow/task-queue.md` |

Если источники противоречат друг другу, не выбирать произвольный вариант.

## 4. Реестр решений

На текущем этапе не фиксировать неподтверждённые технические решения как окончательные.

| ID | Решение | Статус |
|---|---|---|
| DEC-001 | Существующую архитектуру нельзя менять без обоснования | Принято как правило разработки |
| DEC-002 | Дизайн-система должна опираться на анализ референсов и текущего frontend | Принято как процесс |
| DEC-003 | Роли должны иметь разграниченные обязанности и зоны изменений |
