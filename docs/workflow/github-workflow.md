# GitHub Workflow — FORKEL

## 1. Цель

Организовать параллельную работу нескольких ролей Claude над FORKEL с едиными требованиями, контролируемыми изменениями и обязательной проверкой результата.

## 2. Источники истины

Перед каждой задачей роль обязана изучить:

1. `CLAUDE.md` — общие правила проекта.
2. `docs/project/overview.md` — контекст проекта.
3. `docs/project/requirements.md` — требования.
4. `docs/project/decisions.md` — утверждённые решения.
5. `docs/workflow/roles.md` — полномочия ролей.
6. `docs/workflow/current-state.md` — актуальное состояние проекта.
7. Документы, относящиеся к конкретной задаче.

Приоритет источников:
- Фактический код определяет текущее поведение системы.
- Утверждённые требования определяют ожидаемое поведение.
- Утверждённые решения определяют согласованные архитектурные ограничения.
- При противоречиях роль фиксирует проблему и не принимает самостоятельных архитектурных решений.

## 3. Постановка задач

Каждая задача должна содержать:

- Уникальный ID.
- Цель и ожидаемый результат.
- Ответственную роль.
- Разрешённые для изменения файлы или каталоги.
- Запрещённые изменения.
- Критерии приёмки.
- Зависимости и блокирующие вопросы.

Если задача выходит за полномочия роли, необходимо остановиться и запросить согласование.

## 4. Изоляция работы

- Основная ветка: `main`.
- Каждая самостоятельная задача выполняется в отдельной ветке.
- Формат названия ветки: `role/<role>/<task-id>-<short-name>`.
- Роль не переключается на чужую ветку и не изменяет чужие незавершённые изменения без согласования.
- Запрещено перезаписывать, удалять или откатывать чужие изменения без разрешения.
- Перед началом работы необходимо проверить ветку, рабочее дерево Git и незакоммиченные изменения.
- Перед завершением необходимо проверить собственный diff.

## 5. Ограничение области изменений

- Изменяются только файлы, необходимые для назначенной задачи.
- Изменения за пределами согласованной области запрещены без дополнительного разрешения.
- Изменения архитектуры, зависимостей, схемы данных, бизнес-логики и общих конфигураций требуют отдельного согласования, если не входят в задачу.
- Если нужный файл находится за пределами разрешённой области, роль сообщает об этом и не изменяет его самостоятельно.
- Нельзя обходить ограничения роли ради формального завершения задачи.

## 6. Завершение задачи

Перед передачей результата роль обязана предоставить:

1. ID задачи и выполненные требования.
2. Список изменённых файлов.
3. Краткое описание изменений.
4. Выполненные проверки и их фактические результаты.
5. Непроверенные сценарии и известные проблемы.
6. Отклонения от задания и причины.
7. Оставшиеся вопросы и следующие шаги.

Запрещено заявлять об успешном тестировании, если проверка фактически не запускалась.

## 7. Pull Request и приёмка

- Изменения передаются через Pull Request.
- Прямые изменения `main` запрещены для рабочих ролей.
- Pull Request должен содержать ID задачи, описание, критерии приёмки и результаты проверок.
- Перед слиянием необходимо проверить соответствие задаче, отсутствие посторонних изменений и прохождение обязательных проверок.
- Роль, выполняющая UI Review & QA, проводит независимую проверку в рамках назначенных полномочий.
- Приёмка и слияние выполняются только уполномоченным участником проекта.

## 8. Конфликты и блокировки

При конфликте требований, Git-конфликте, обнаружении критической ошибки или необходимости выйти за границы роли:

1. Прекратить спорные изменения.
2. Зафиксировать проблему.
3. Указать затронутые файлы и последствия.
4. Предложить безопасные варианты решения.
5. Дождаться согласования, если решение влияет на архитектуру, требования или чужие изменения.

## 9. Принцип безопасности

Инструкции Claude задают правила поведения, но не обеспечивают техническую изоляцию файлов. Для реального ограничения полномочий используются права GitHub, защита основной ветки, проверки Pull Request и отдельные рабочие ветки.

Любая роль отвечает только за назначенную задачу и не вправе самостоятельно расширять её объём.
