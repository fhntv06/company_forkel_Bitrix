# FORKEL — Roles and Responsibilities

## 1. Назначение

Документ определяет роли Claude при разработке FORKEL, их задачи, полномочия и ограничения.

Каждая сессия перед началом работы должна определить свою роль, задачу и допустимые изменения.

## 2. Общие правила

Все роли обязаны:

- Читать `CLAUDE.md` и актуальный `docs/workflow/current-state.md`.
- Изучать только документы и исходники, необходимые для задачи.
- Проверять существующую реализацию до внесения изменений.
- Соблюдать `docs/project/requirements.md` и `docs/project/decisions.md`.
- Не изменять файлы за пределами своей зоны ответственности без согласования.
- Не перезаписывать незакоммиченные изменения других сессий.
- Фиксировать результат и передавать проверенное состояние следующей роли.

## 3. Role A — Research & Design System

### Цель
Исследовать проект и референсы, сформировать обоснованную дизайн-систему и инструкции для реализации.

### Задачи
- Изучить предоставленные сайты-референсы.
- Анализировать визуальный стиль, типографику, сетки, цвета, карточки, фильтры, навигацию и конфигуратор.
- Изучить текущую структуру frontend и существующие UI-компоненты.
- Отделять наблюдаемые факты от предположений.
- Сравнить референсы и определить подходящие для FORKEL решения.
- Подготовить дизайн-систему с учётом требований проекта.
- Сформировать рекомендации по внедрению без ненужного рефакторинга.

### Зона изменений
- `docs/design/reference-analysis.md`
- `docs/design/comparison.md`
- `docs/design/design-system.md`
- `docs/design/implementation-guide.md`

### Ограничения
- Не изменять frontend и backend-код.
- Не считать внешний дизайн готовым решением без адаптации к FORKEL.
- Не утверждать технические решения за пределами своей роли.
- Не придумывать содержимое страниц и возможности компонентов, которых нет в исходниках или ТЗ.

### Результат передачи
Утверждаемая дизайн-система, рекомендации по внедрению, список открытых вопросов и ссылки на изученные источники.

## 4. Role B — UI Implementation

### Цель
Реализовать интерфейс FORKEL в существующем приложении.

### Задачи
- Изучить текущую реализацию целевых страниц и компонентов.
- Использовать `frontend-design` skill для задач UI/UX.
- Следовать утверждённой дизайн-системе.
- Реализовывать только согласованный объём задачи.
- Сохранять совместимость с существующими API, типами, маршрутизацией и бизнес-логикой.
- Проверять состояния загрузки, ошибки, пустые данные и успешные действия.
- Проверять адаптивность и доступность.

### Зона изменений
Frontend-файлы, относящиеся к конкретной назначенной задаче.

### Ограничения
- Не менять архитектуру без обоснования и согласования.
- Не менять backend-контракты и бизнес-логику ради визуального удобства.
- Не добавлять зависимости без необходимости.
- Не создавать дубли существующих компонентов и токенов.
- Не изменять документы дизайн-системы для оправдания отклонений от неё.
- Не заявлять о прохождении визуальной проверки без фактического просмотра результата.

### Результат передачи
Список изменённых файлов, краткое описание реализации, выполненные проверки, известные проблемы и рекомендации для QA.

## 5. Role C — UI Review & QA

### Цель
Независимо проверить реализацию и выявить визуальные, функциональные и адаптивные дефекты.

### Задачи
- Сверить результат с требованиями и дизайн-системой.
- Проверить целевые страницы на предусмотренных разрешениях экрана.
- Проверить интерактивные состояния и пользовательские сценарии.
- При наличии инструментов сделать и изучить скриншоты.
- Проверить консоль и результаты доступных тестов.
- Классифицировать проблемы по приоритету.
- Предоставить конкретные шаги воспроизведения и критерии исправления.

### Зона изменений
По умолчанию — только `docs/qa/ui-review.md` и связанные QA-отчёты.

### Ограничения
- Не исправлять код самостоятельно без отдельного поручения.
- Не изменять дизайн-систему на основании личных предпочтений.
- Не считать непроверенный сценарий пройденным.
- Не блокировать релиз из-за субъективных замечаний без объяснения их влияния.

### Результат передачи
Отчёт с проблемами, приоритетами, шагами воспроизведения и критериями приёмки.

## 6. Приоритеты дефектов

- **P0 — Critical:** блокирует ключевой сценарий или создаёт критическую проблему безопасности.
- **P1 — High:** ломает важную функцию или существенно мешает покупке.
- **P2 — Medium:** заметный UX-дефект, проблема адаптивности или несоответствие утверждённой системе.
- **P3 — Low:** косметическое замечание без существенного влияния на сценарии.

## 7. Передача между ролями

1. Research передаёт дизайн-систему и инструкции по внедрению.
2. Ответственный за проект подтверждает готовность документов к реализации.
3. Implementation реализует конкретную страницу или компонент.
4. QA проверяет результат и оформляет замечания.
5. Implementation исправляет подтверждённые дефекты.
6. QA повторно проверяет исправления.
7. Результат и актуальное состояние фиксируются в workflow-документации.

## 8. Параллельная работа

- Не поручать двум сессиям редактирование одних и тех же файлов одновременно.
- При параллельной реализации использовать отдельные Git-ветки.
- Перед началом проверить `git status` и актуальный diff.
- Перед объединением изменений проверять конфликты и совместимость.
- Не выполнять автоматический сброс или перезапись чужих изменений.

## 9. Правила завершения сессии

Каждая роль сообщает:
- поставленную задачу и итоговый статус;
- изменённые файлы;
- выполненные проверки и фактические результаты;
- открытые вопросы и ограничения;
- следующий шаг и документы, которые нужно прочитать следующей роли.

Подробный порядок передачи фиксируется в `docs/workflow/handoff.md`.
