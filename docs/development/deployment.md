# Регламент: выкладка и миграции (локально → боевой сайт)

Статус: действует с 2026-11-27. Инструмент миграций: **sprint.migration 5.16.1**.

## 1. Принцип: что где живёт

| Что | Источник правды | Как попадает на боевой |
|---|---|---|
| Код: шаблоны, компоненты, CSS/JS (`backend/www/local/`), файлы страниц (`projects/index.php` и т.п.) | Git | выкладка файлов из Git |
| Структура данных и настройки: инфоблоки, свойства, HL-блоки, опции модулей, оплата/доставка, группы, почтовые события | Миграции в Git | `migrate.php up` на боевом |
| Контент: тексты, проекты, баннеры, картинки | **Боевой сайт** (админка) | вводится на боевом |
| Каталог, цены, остатки | **1С** | обмен CommerceML |
| Заказы, пользователи | **Боевой сайт** | никогда не переносятся с локального |
| Тестовые данные (демо-товары) | Миграции `testdata` | **никогда** — только локально |

> **Главное правило.** После запуска боевого сайта локальная база на боевую **не заливается никогда**: потеряются заказы и контент. Структура меняется только миграциями. Изменения структуры руками в админке боевого сайта запрещены (иначе локальная и боевая структуры разойдутся).

Код ищет инфоблоки по символьному коду (`fk_iblock_id('projects')`), а не по ID. В миграциях тоже используем коды (CODE / XML_ID), а не числовые ID.

## 2. Как устроены миграции

- Модуль: `backend/www/local/modules/sprint.migration/`. Лежит в Git, версия зафиксирована: 5.16.1, источник — github.com/andreyryabin/sprint.migration, тег `5.16.1`. Обновлять осознанно, отдельной задачей.
- Конфигурации (в `backend/www/local/php_interface/`):

| Конфиг | Файл | Папка миграций | Таблица в БД | Где применяется |
|---|---|---|---|---|
| `cfg` (основной) | `migrations.cfg.php` | `migrations/` | `sprint_migration_versions` | везде |
| `testdata` | `migrations.testdata.php` | `migrations.testdata/` | `sprint_migration_testdata` | только `APP_ENV=local` |

Конфиг `testdata` при `APP_ENV` ≠ `local` (или если переменная не задана) просто не загружается. На боевом его миграции не видны и случайно не запустятся.

Журнал применённых миграций хранится в БД сайта. Поэтому при первом переносе (раздел 4) боевой сайт сразу «знает», что текущие миграции уже применены.

## 3. Команды

Запускаются из корня сайта (DOCUMENT_ROOT). Локально — внутри контейнера:

```bash
# локально (из корня репозитория)
docker exec -w /var/www/html forkel-php php local/modules/sprint.migration/tools/migrate.php <команда>

# на сервере (из корня сайта, от пользователя веб-сервера)
php local/modules/sprint.migration/tools/migrate.php <команда>
```

| Команда | Действие |
|---|---|
| `ls` / `ls --new` | список миграций / только неприменённые |
| `up` | применить все новые миграции основного конфига |
| `up --config=testdata` | применить тестовые данные (только локально) |
| `add "описание"` | создать пустую миграцию |
| `mark <Version> --as=installed` | отметить как применённую без запуска |
| `config` | показать настройки |

Админка: **Сервисы → Миграции для разработчиков** (`/bitrix/admin/sprint_migrations.php`). Там же есть конструкторы миграций.

Если модуль ещё не установлен в Битриксе, первый же запуск `migrate.php` установит его сам. Известная особенность: этот первый запуск может завершиться ошибкой `Config already exists: testdata`. Это разово, просто повторите команду.

## 4. Этап 1 — первый запуск боевого сайта (один раз)

Первый запуск — это перенос сайта **целиком** (файлы + БД), а не чистая установка с прогоном миграций. Инфоблоки, настройки магазина и контент создавались частично вручную. Полностью их воспроизводит только копия БД.

**Подготовка (локально)**
1. Все изменения закоммичены и смержены. `migrate.php ls --new` — пусто (всё применено).
2. Удалить тестовые данные, которые не должны попасть на боевой: бета-товары и торговые предложения (`f70-*`, `f55-*`, `tp-test-*`), тестовые заказы, корзины, тестовые пользователи, проекты «Проект тест N» — или получить решение владельца оставить их. Удалять только после резервной копии.
3. **Настройки → Инструменты → Резервное копирование**: полная копия (файлы + БД).

**Перенос (боевой сервер)**
4. Сервер соответствует требованиям редакции «Малый бизнес» (проверить `/bitrix/admin/site_checker.php` после восстановления).
5. Восстановить через `restore.php`, указать доступы к боевой БД. После восстановления удалить `restore.php` и архив.
6. **Ввести лицензионный ключ**: Настройки → Настройки продукта → Система обновлений. Поставить обновления ядра и модулей.
7. Привязать Git: дальше файлы из репозитория (`local/`, файлы страниц) выкладываются поверх. `bitrix/` и `upload/` в Git не лежат и при выкладке не трогаются.
8. Окружение (переменные сервера или `.env` рядом с корнем сайта; см. `backend/.env.example`):
   - `APP_ENV=production`, `APP_DEBUG=0`;
   - боевые ключи ЮKassa / СДЭК, `PAYMENT_SANDBOX=0`, `CDEK_SANDBOX=0`;
   - SMTP, `YANDEX_MAPS_API_KEY`, `MAX_*`.

**Проверка после переноса**
9. `migrate.php ls --new` — пусто. `migrate.php ls --config=testdata` — конфиг не найден (так и должно быть при `APP_ENV=production`).
10. Проверить HTTPS, `robots.txt` и `sitemap.xml` (домен!), почту, корзину и оформление заказа, оплату в боевом режиме, обмен с 1С.
11. Задать пароль техническому пользователю `1c_exchange` и сменить пароль администратора.
12. Включить регулярное резервное копирование боевой БД и `upload/`.

## 5. Этап 2 — обычная работа после запуска

### Как сделать изменение структуры (локально)

Пример: нужно новое свойство товара.

**Вариант А (удобный): конструктором из админки**
1. Локально создать свойство в админке как обычно.
2. **Сервисы → Миграции для разработчиков → Конструкторы → «Свойства инфоблока»** (или «Инфоблок», «Опции», «Свойства заказа», «Группы пользователей» и т.д.). Конструктор сгенерирует файл миграции в `local/php_interface/migrations/`.
3. Проверить файл: он должен искать инфоблок по коду, а не по ID (хелперы sprint делают это сами).

**Вариант Б: вручную**
1. `migrate.php add "Добавить свойство POWER в каталог"` — создаст заготовку.
2. В `up()` писать через хелперы, например:
   ```php
   $helper = $this->getHelperManager();
   $iblockId = $helper->Iblock()->getIblockIdIfExists('catalog', 'catalog');
   $helper->Iblock()->saveProperty($iblockId, [
       'NAME' => 'Мощность', 'CODE' => 'POWER', 'PROPERTY_TYPE' => 'S', 'FILTRABLE' => 'Y',
   ]);
   ```
   Хелперы `save*` идемпотентны: создают или обновляют.

**Далее в обоих вариантах**
- Локально проверить `up`. Хорошая практика: `mark <Version> --as=new` → `up` ещё раз, чтобы убедиться, что повторный запуск ничего не дублирует.
- Закоммитить миграцию **в той же ветке/PR**, что и код, который от неё зависит.

### Как выкладывать на боевой

1. **Резервная копия БД** боевого сайта (обязательно, откат делается из неё).
2. Выложить файлы из Git (смерженный `main`).
3. `php local/modules/sprint.migration/tools/migrate.php ls --new` — посмотреть, что будет применено.
4. `php local/modules/sprint.migration/tools/migrate.php up`.
5. Очистить кеш (Настройки → Настройки продукта → Автокеширование → Очистка файлов кеша).
6. Проверить главную, каталог, карточку товара, корзину и те страницы, которые затронула выкладка.

Если миграция упала: sprint не отметит её применённой. Исправить причину (локально, через PR) и повторить `up`. Если она успела частично изменить данные некорректно — восстановить БД из копии шага 1.

## 6. Правила написания миграций

- **Идемпотентность.** Повторный запуск не создаёт дублей. Существование проверяем по устойчивому ключу (CODE / XML_ID / STRING_ID). Учтите: Битрикс перезаписывает `CODE` службы доставки на её ID. Для доставок используем `XML_ID`.
- **Никаких числовых ID** инфоблоков, свойств, групп — они различаются между окружениями. (Исключение — исторические миграции TASK-018: они рассчитаны на текущую БД, которая целиком переедет на боевой.)
- **Никаких секретов в коде.** Пароли и ключи — из окружения (`\Forkel\Env::get(...)`).
- **Структура ≠ тестовые данные.** Демо-товары, тестовые заказы, тестовые пользователи — только в `migrations.testdata/` (`add "..." --config=testdata`).
- **Не трогать контент и заказы** в основных миграциях. Исключение — согласованная с владельцем миграция данных с отдельным планом отката.
- **Удаления — только осознанно.** Удаление свойства или инфоблока уничтожает данные на боевом. Нужны отдельная миграция, резервная копия и явное решение владельца.
- **Применённую миграцию не редактируем.** Нужно что-то исправить — пишем новую. sprint хранит хеш файла и покажет изменённые.
- `down()`: если откат безопасен (например, добавлено пустое свойство) — реализуем. Иначе выбрасываем исключение с пояснением, как в миграциях TASK-018.

## 7. Новое локальное окружение разработчика

Пока сами инфоблоки не описаны миграциями, новое окружение разворачивается из дампа БД (без персональных данных) + `upload/`. После разворачивания: `migrate.php up`, затем, если нужны демо-данные, `migrate.php up --config=testdata`.

## 8. Известные вопросы (на 2026-11-27)

- **Дубли доставки СДЭК — устранено (2026-11-27).** Старый скрипт блока 3 при каждом запуске создавал новую службу «СДЭК». Лишние #5 и #7 удалены из локальной БД (отправлений на них не было). Рабочая служба — #6 с `XML_ID = forkel_cdek`. Миграция `Version20261127100100` ищет её по `XML_ID` и дублей не создаёт.
- **Платёжные системы ЮKassa в режиме Sandbox.** На боевом переключить в боевой режим (шаг 8 раздела 4).
- **`console_user = admin`.** Консольные миграции выполняются от пользователя с логином `admin`. Если на боевом логин администратора другой — добавить `'console_user' => 'логин'` в `migrations.cfg.php`.
- **Инфоблоки (8 шт.) созданы вручную** и миграциями не описаны. Для этапа 1 это не мешает: они переедут с БД. При желании можно сделать базовую миграцию конструктором «Инфоблок» и отметить её применённой (`mark ... --as=installed`).
