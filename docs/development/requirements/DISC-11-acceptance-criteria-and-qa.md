# DISC-11 — Acceptance Criteria and QA

## 1. Purpose

Документ устанавливает правила проверки сайта Forkel и критерии приемки требований, страниц и пользовательских сценариев.

## 2. General acceptance principles

Функциональность принимается, когда:
- Она соответствует утвержденным требованиям.
- Основной сценарий выполняется корректно.
- Существенные альтернативные сценарии проверены.
- Ошибки обрабатываются предусмотренным образом.
- Реализация не нарушает согласованное поведение других компонентов.
- Результат можно воспроизвести и проверить.

Неподтвержденные требования не считаются автоматически принятыми.

## 3. Test levels

При необходимости использовать следующие уровни:
- Component tests.
- Integration tests.
- End-to-end tests.
- Responsive checks.
- Accessibility checks.
- SEO validation.
- Performance checks.
- Security checks.

Конкретная стратегия тестирования согласовывается с инженерной командой.

## 4. Navigation checks

Проверить:
- Работу основных ссылок.
- Переходы между страницами.
- Работу Header и Footer.
- Поведение навигации на мобильных устройствах.
- Корректность прямого открытия URL.
- Обработку неизвестных адресов.

## 5. Projects checks

Проверить:
- Отображение списка проектов.
- Соответствие карточек данным.
- Переход к детальной странице.
- Корректность содержимого выбранного проекта.
- Поведение при отсутствии необязательных полей.
- Обработку неизвестного проекта.

## 6. Search checks

Если поиск утвержден, проверить:
- Ввод запроса.
- Запуск поиска.
- Наличие результатов.
- Отсутствие результатов.
- Пустой запрос.
- Ошибку поиска.
- Переход к результату.
- Клавиатурное взаимодействие с модальным окном.

## 7. Feedback form checks

Проверить:
- Отображение полей.
- Обязательные поля.
- Невалидные значения.
- Корректные значения.
- Отправку формы.
- Loading state.
- Предотвращение повторной отправки.
- Успешный результат.
- Ошибку отправки.
- Безопасную обработку пользовательского ввода.

## 8. Responsive checks

Проверить ключевые сценарии на согласованных размерах экрана и поддерживаемых браузерах.

Проверить:
- Отсутствие непредусмотренной горизонтальной прокрутки.
- Читаемость текста.
- Доступность CTA.
- Поведение карточек и сеток.
- Модальные окна.
- Формы и поля ввода.
- Навигацию.

## 9. Accessibility checks

Проверить:
- Клавиатурную навигацию.
- Видимый фокус.
- Подписи полей.
- Связь ошибок с полями.
- Доступность модальных окон.
- Альтернативные тексты изображений.
- Контрастность и структуру заголовков.

## 10. Defect severity

Предварительная классификация:

- Critical — блокирует основную функциональность или создает серьезный риск.
- Major — нарушает важный пользовательский сценарий.
- Minor — ограниченная проблема с доступным обходным путем.
- Cosmetic — визуальное отклонение без существенного влияния на использование.

Классификацию и допустимый уровень дефектов перед релизом необходимо согласовать.

## 11. Test case template

Для каждого теста фиксировать:
- Test ID.
- Связанный Requirement ID.
- Предусловия.
- Шаги.
- Ожидаемый результат.
- Фактический результат.
- Статус.
- Среду проверки.
- Ссылку на дефект, если обнаружен.

## 12. Release readiness

Перед релизом проверить:
- Закрытие блокирующих дефектов.
- Проверку критических сценариев.
- Корректность контента и контактов.
- Работу форм и интеграций.
- Responsive behavior.
- SEO-настройки.
- Аналитику, если утверждена.
- Готовность согласованных окружений.

Финальный допуск к релизу остается за ответственными участниками проекта.
