# DISC-05 — Components and Interactions

## 1. Purpose

Документ описывает поведение повторно используемых компонентов и интерактивных элементов сайта Forkel.

## 2. General principles

Общие компоненты должны:
- Иметь согласованное назначение.
- Использовать единые правила поведения.
- Поддерживать требуемые состояния.
- Быть пригодными для повторного использования.
- Работать на поддерживаемых устройствах.
- Учитывать клавиатурную навигацию и доступность.

Визуальные параметры определяются в согласованной дизайн-системе.

## 3. Component inventory

| Component ID | Component | Specification |
|---|---|---|
| CMP-HEADER | Header | Навигация и глобальные действия |
| CMP-FOOTER | Footer | Нижняя навигация и контактные сведения |
| CMP-BUTTON | Button | Действия пользователя |
| CMP-LINK | Link | Переходы между страницами и ресурсами |
| CMP-PROJECT-CARD | Project card | Представление проекта |
| CMP-MODAL | Modal | Общая логика модальных окон |
| CMP-SEARCH | Search input | Ввод поискового запроса |
| CMP-FORM | Form | Ввод и отправка данных |
| CMP-FORM-FIELD | Form field | Поля ввода и валидация |
| CMP-FEEDBACK | Feedback form | Обратная связь |
| CMP-MAP | Map | Отображение местоположения, если требуется |

Состав является предварительным.

## 4. Button

Определить:
- Назначение и действие.
- Варианты представления.
- Default, hover, focus, active и disabled states.
- Loading state для асинхронных действий.
- Правила недопущения повторной отправки.
- Клавиатурное взаимодействие.

Навигацию следует реализовывать как ссылку, если действие семантически является переходом.

## 5. Modal

Общие требования:
- Открытие по согласованному действию.
- Видимый способ закрытия.
- Управление фокусом.
- Закрытие по Escape, если применимо.
- Корректное поведение при открытии с клавиатуры.
- Предотвращение некорректного взаимодействия с фоновым содержимым.
- Адаптивное представление.

Отдельно определить, закрывается ли окно по клику вне его области. Не предполагать это поведение автоматически.

## 6. Search interaction

Описать:
- Ввод запроса.
- Правило запуска поиска.
- Минимальную длину запроса, если требуется.
- Обработку пустого ввода.
- Состояние загрузки.
- Отображение результатов.
- Пустую выдачу.
- Ошибки.
- Очистку поля.
- Переход к результату.

Правила поиска и состав индексируемого контента согласовываются отдельно.

## 7. Form interaction

Для каждой формы определить:
- Список полей.
- Тип каждого поля.
- Обязательность.
- Правила валидации.
- Тексты ошибок.
- Состояние отправки.
- Успешный результат.
- Ошибку отправки.
- Поведение после ошибки.
- Предотвращение повторной отправки.

Клиентская валидация не заменяет серверную проверку.

## 8. Feedback modal states

Предусмотреть следующие состояния, если они применимы:
- Closed.
- Open / Initial.
- Validation error.
- Submitting.
- Success.
- Submission error.

Переходы между состояниями должны быть определены явно.

Успешное сообщение пользователю допускается только после подтвержденной успешной обработки запроса.

## 9. Project card

Определить:
- Набор отображаемых данных.
- Изображение и его fallback.
- Заголовок и дополнительный текст.
- Ссылку на детальную страницу.
- Hover и focus states.
- Поведение на мобильных устройствах.

Карточка не должна обещать функциональность, не предусмотренную требованиями.

## 10. Accessibility

Проверить:
- Семантические элементы.
- Клавиатурную навигацию.
- Видимый фокус.
- Подписи полей.
- Связь сообщений об ошибках с полями.
- Достаточную контрастность.
- Доступность модальных окон.
- Альтернативный текст изображений.

Конкретный целевой стандарт доступности определяется владельцем проекта.

## 11. Error handling

Сообщения об ошибках должны быть понятными и не раскрывать внутренние технические сведения.

Если пользователь может исправить ошибку, интерфейс должен позволять выполнить исправление.
